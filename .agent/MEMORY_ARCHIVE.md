# 🗄️ Архив инженерных разборов (Root Cause Analysis — Lgraph)

### RC-01: Потеря параллельных связей при узком составном ключе в БД графа (`G-06`)
- **Суть:** Ключ таблицы `edges` без поля `evidence` перезаписывал второй IPC-канал между теми же модулями.
- **Решение:** В составной `PRIMARY KEY` включено поле `evidence`.

### RC-02: Типизация сторонних пакетов `elkjs`, `lucide-react` и `mcp_types` v2 (`G-07`)
- **Суть:** Несовпадение деклараций `elkjs/lib/elk.bundled.js` при `tsc -b` и переход SDK `mcp` v2 на пакет `mcp_types` со `snake_case`-атрибутами.
- **Решение:** Добавлена декларация модуля в `vite-env.d.ts` и прямые импорты `mcp_types.ToolAnnotations`.

### RC-03: Нативный сбой C ABI при смешении разных поколений `tree-sitter` (`G-08`)
- **Суть:** Смешение ядра `tree-sitter 0.26` (ABI 15) и грамматик `0.23.2` (ABI 14).
- **Решение:** Версии синхронизированы диапазоном `>=0.23.2,<0.25.0` под единым `threading.Lock()`.

### RC-04: Наследование `ELECTRON_RUN_AS_NODE=1` от родительских Electron-IDE (`G-09`)
- **Суть:** Терминалы VS Code / Cursor / Antigravity экспортируют `ELECTRON_RUN_AS_NODE=1`, переводя дочерний `electron.exe` в режим консольного Node.js.
- **Решение:** Принудительный сброс `set ELECTRON_RUN_AS_NODE=` в `START_APP.bat` и `lgraph.cmd`.

### RC-05: Размытие весов `PageRank` на синтетических рёбрах `c4_rollup` (`G-10`)
- **Суть:** Визуальные агрегирующие рёбра `C3` попадали в расчёт кодовых зависимостей.
- **Решение:** Исключение `source_module == "c4_rollup"` и `CONTAINS` из аналитических обходов.

### RC-06: Просачивание секрета через дефолтный аргумент функции в `signature` (`G-11`)
- **Суть:** Строковый ключ в параметре по умолчанию попадал в поле `signature`, минуя очистку докстрингов.
- **Решение:** Двухконтурная санитизация всех строковых полей узлов и рёбер в парсерах и `GraphRepository`.

### RC-07: Автономный режим `MCP` без параметра `cwd` и открытого окна UI (`G-12`)
- **Суть:** Схема `mcp_config.json` не гарантирует рабочую директорию `cwd`, а при закрытом UI фоновый `Watchdog` не запущен.
- **Решение:** Самонастраивающийся загрузчик `run_mcp_server.py` + быстрая проверка метаданных файлов `is_project_disk_dirty` (`~2–4 мс`).

### RC-08: Особенности Windows Shell (`wscript.exe`, `CP866` в `.cmd`, апострофы в `powershell -Command`) (`G-14`)
- **5 Почему:**
  1. Почему `lgraph-editor:open-file` с `shell.openPath` и `build_windows_shortcuts.py` с `f-строкой` создавали риск при анализе сторонних проектов и нестандартных путях ОС?
  2. Потому что `shell.openPath` на Windows делегирует глагол `open` в `ShellExecuteExW`, где `.js` ассоциирован с `wscript.exe`, `cmd.exe` по умолчанию читает `.cmd` в `CP866`, а апостроф `'` в пути пользователя рвёт одинарную кавычку PowerShell.
  3. Почему лексический `path.resolve` пропускал симлинки внутри проекта? Потому что он не разрешает NTFS Junctions / symlinks на диске.
  4. **Корень:** Доверие строковым операциям с путями и дефолтным обработчикам оболочки Windows без канонического разрешения ФС и изоляции аргументов через `env`.
- **Решение:** Внедрены `fs.realpathSync.native` + `shell.showItemInFolder`, передача путей в PowerShell строго через `env` и переключение `chcp 65001 >nul` в `START_APP.bat` и `lgraph.cmd`.

### RC-09: Межпроцессные гонки SQLite WAL, `Fail-Closed` конфиг, кодировка `.bat`/`PowerShell` и блокировка `WinError 32` (`G-14`, `G-15`)
- **5 Почему:**
  1. Почему при конкурентной работе UI-демона и `MCP`-сервера, поломке `lgraph.yaml`, не-ASCII байтах в `SETUP.bat`, `PYTHONUTF8=1` с кириллическим `Desktop` и обновлении плагинов при открытой IDE возникали сбои?
  2. Потому что `DEFERRED`-транзакция SQLite брала блокировку записи после `SELECT revision`, ошибка YAML тихо подменялась на `[]`, `cmd.exe` сдвигал указатель на UTF-8 в `if (...)`, `powershell.exe` 5.1 выводил кириллический путь `Write-Output` в OEM `CP866` при чтении через `UTF-8`, а `shutil.rmtree` падал с `WinError 32` на финальном `os.rmdir` корневой папки плагина, удерживаемой `ReadDirectoryChangesW` watcher'ом IDE.
  3. Почему удаление заметки воскрешало старый текст, а `shutil.rmtree` оставлял пустую папку плагина? Потому что пустая `summary_ru` не синхронизировала все 3 таблицы БД, а `rmtree` удаляет вложенные файлы до попытки удалить заблокированный корень.
  4. Почему эти дефекты не ловились синтетическими тестами? Потому что мок-тесты не запускали 2 реальных процесса SQLite, дочерний Python с `PYTHONUTF8=1` на кириллической папке и Win32-дескриптор директории без `FILE_SHARE_DELETE`.
  5. **Корень:** Отсутствие явной `Fail-Closed`-политики, согласования кодировок каналов `stdout` подпроцессов и in-place обновления директорий на межпроцессных границах ОС Windows.
- **Решение:** Введены `BEGIN IMMEDIATE` до чтения ревизии с синхронной очисткой заметок и маскировкой секретов, `Fail-Closed` проверка `lgraph.yaml`, `ToolError` в `MCP` v2 и `HTTP 422` в REST, чистый ASGI `LocalPerimeterMiddleware`, посегментный блок NTFS Junctions + `taskkill /T /F`, 7-bit ASCII + `CRLF` для `.bat`, `[Console]::OutputEncoding = UTF8` в PowerShell и in-place синхронизация `_sync_plugin_dir` без удаления корневой папки плагина.
